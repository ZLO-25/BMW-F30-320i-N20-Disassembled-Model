# 效能基準（E0）

量測基準：main `42879bb`（含 R1、R2），自排變體，headless Chromium + SwiftShader（雲端容器沒有顯示卡）。
重跑：`npm run build && PW_CHROMIUM=/opt/pw-browsers/chromium npm run perf`（約 8 分鐘），原始數據在 `docs/perf/latest.json`。

> **怎麼讀這張表**：軟體繪圖下「每格毫秒」只能比大小，不是真實 FPS。個數類（draw call、三角形、程式數、貼圖數、閒置重繪）是準的。
> 真實 FPS 請用下面的「實機」表。

## 1. Headless 數字（E0 之前，視窗 1000×640、dpr 1）

| 項目 | high | mid | low |
| --- | --- | --- | --- |
| 場景三角形（合併後） | 665,862 | 223,230 | 79,620 |
| mesh 數 | 412 | 411 | 408 |
| 每格 draw call | 1,630 | 405 | 372 |
| 每格送去畫的三角形 | 2,605,876 | 228,309 | 76,270 |
| 著色器程式數（遠） | 35 | 32 | 18 |
| 貼圖數 | 45 | 29 | 9 |
| JS 記憶體 | 80 MB | 53 MB | 45 MB |
| 連續畫時每格 p50（軟體繪圖，只比大小） | 2,117 ms | 567 ms | 233 ms |
| **閒置 3 秒畫了幾格** | 2（軟體繪圖太慢，實際是「一直在畫」） | 5 | 12 |
| 最長的長工作 | 9,962 ms | 6,302 ms | 4,717 ms |

> high 的 draw call 1,630 比規劃文件量到的 791 多，因為 R2 加了零件（mesh 399 → 412、三角形 636k → 666k），
> 而且這次 `calls` 統計把後處理的全螢幕 pass 與陰影 pass 都算進去（U6 之後 PerfStats 改成每格累計）。比較前後請用同一份工具量。

### F11 驗證：拉近鏡頭會重新編譯著色器（已證實）

鏡頭從 3.6 m 拉到 1.5 m（工作燈亮起）：

| | 遠 | 近 | 增加 |
| --- | --- | --- | --- |
| high | 35 | 52 | +17 |
| mid | 32 | 49 | +17 |
| low | 18 | 35 | +17 |

→ 每次第一次拉近都要多編譯 17 支著色器，會頓一下。E1 修。

### F12 驗證：切換變速箱 6 次（貼圖漏失）

| | 貼圖 前 → 後 | 幾何 前 → 後 |
| --- | --- | --- |
| high | 45 → 69（+24） | 416 → 428（+12） |
| mid | 29 → 53（+24） | 415 → 427（+12） |
| low | 9 → 9（0，low 沒有接觸陰影） | 409 → 409 |

→ 漏失只發生在有接觸陰影的畫質，證實來源是 `SoftContactShadows`（每次用 `key` 重掛都留下一張渲染目標）。E1 修。

## 1b. E0–E5 之後（同一把尺，同樣 headless，main 已含 R3–R5）

> R3–R5 同時合併進來，場景內容變多了（high 三角形 666k → 704k 主要是新車殼與引擎運轉零件），所以三角形、mesh 數不能直接當作「優化效果」；
> 效果看「閒置重繪、程式數、貼圖、首包、射線、介面」這些項目。

| 項目 | E0（42879bb） | 現在 | 達標？ |
| --- | --- | --- | --- |
| 閒置 3 秒畫了幾格 | 持續重畫（每秒 ~60 次） | **0**（high / mid / low） | ✅ 目標 0 |
| 拉近鏡頭後的著色器程式數 | 35 → 52（+17） | 54 → 54（+0） | ✅ F11 已修 |
| 切換變速箱 6 次後貼圖 | 45 → 69（+24） | 43 → 43（+0） | ✅ 目標 0 |
| 切換變速箱 6 次後幾何 | 416 → 428（+12） | 460 → 460（+0） | ✅ |
| 首次進站 JS（gzip） | 622 KB | **513 KB**（另外延遲載入：後處理 100 KB、教學資料 39 KB） | ⚠ 目標 500，差 13 KB |
| 一次射線檢查（mid，30 次平均） | 3.7 ms（無 BVH，`?bvh=0`） | **0.7 ms**（BVH）；low 1.2 ms | ✅ 目標 < 4 ms（原估 16 ms 是整段 JS 含 React，射線本身只佔 3.7 ms） |
| BVH 建樹時間 | — | high 291 ms / mid 90 ms / low 35 ms，**閒置時分批做**，不卡載入 | ✅ |
| 普通格 draw call（mid，不含陰影／接觸陰影） | 405（R2 前的 mid） | 451（R3–R5 多了 29 個 mesh） | — |
| 轉動時 high 的陰影圖 | 每格重畫整台車 | 不重畫（只在有東西動時） | ✅ 每格省一次全車繪製（約 450 次 draw call） |
| 手機 390×844 的 3D 畫面高度 | 328 px | **458 px** | ✅ 目標 420 |
| 手機小於 40 px 的按鈕 | 188 | **1** | ✅ 目標 ≤ 10 |
| 桌機小於 24 px 的按鈕 | 55 | **0** | ✅ |
| 側欄寬 380 px 時分頁折行 | 2 個 | **0** | ✅ |

> 軟體繪圖下 high 每格要 2 秒多，所以 high 的「普通格 draw call」在這個環境量不到乾淨的數字；
> 依程式碼推估：普通格 ≈ 場景 457 個 mesh × 2（主畫面 + AO 的法線／深度）≈ 910，陰影圖那一遍（+457）只在有東西移動時才出現。實機請看 `?bench=1`。
